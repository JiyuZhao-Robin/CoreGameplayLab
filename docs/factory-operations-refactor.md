boundary and deterministic physical inventory authority. Old-save compatibility
is not an acceptance requirement for this refactor. No Git operations requested.

## Product decisions

- Use an authored full-width industrial workspace, like Ship Assembly, with its
  own inspector and build dock. Do not change persisted sidebar choices or scale.
- Default to an operations overview; keep Canvas, Production and Construction
  as persistent views. Real machine silhouettes and contextual status belong on
  the canvas. Never animate absent material flow.
- Use a sovereign command-center voice: `工业统辖中枢 / 以此为基，铸造星海。`
  Status boards report real operating conditions; tutorial prose belongs to the
  existing task guidance system, not the industrial panorama or stage cards.
- A build target explains its bill of materials, stock, deficits and recipe
  dependencies. Expansion means increasing physical production and construction
  capacity; no fictional terrain-reveal or port command is presented.
- Automatically funded construction continues collecting newly produced goods
  from same-world physical storage after order creation. Manual funding remains
  manual; external/local-location transfers remain explicit application commands.
- Verify a new-game mining → processing → storage → construction loop, focused
  domain/UI tests, fixed-layout policy/scale/window matrix and rendered captures.
  Full release/journey umbrellas are not part of this request.

## Optional operations snapshot extension, version 1

`FactoryOperationsProjection.build(snapshot: Dictionary) -> Dictionary` is pure,
detached, deterministic and read-only. `Game.factory_workspace_snapshot()` attaches
its return value at `snapshot.operations` after localization and inventory
enrichment. Existing v1 fields and commands are unchanged. Missing operations
data is supported by older UI fixtures.

```text
operations.schema_version = 1
operations.metrics = {
  extractors, running_machines, blocked_entities, stored_items,
  power_supply_kw, power_demand_kw, active_orders, waiting_orders
}
operations.stages = [{
  id: COLLECTION | PRODUCTION | CONSTRUCTION | EXPANSION,
  state: MISSING | BLOCKED | ACTIVE | READY,
  count: int, action: Action
}]
operations.alerts = [{
  id, code, entity_id?, order_id?, item_id?, amount?, action: Action
}]
operations.materials = [{
  item_id, stored, location_available, buffered, available, required, missing,
  production_per_second, consumption_per_second
}]
operations.build_plans = [{
  definition_id, affordable, work_required, power_demand_kw,
  materials: [{item_id, required, available, missing, producer_building_id, recipe_id}],
  dependencies: [{item_id, depth, recipe_id, building_id, inputs, outputs,
                 kind?: EXTRACTION, resource_field_id?: string, action?: Action}]
}]
Action = {kind: FOCUS_ENTITY | FOCUS_ORDER | SELECT_BUILDING | OPEN_TAB,
          target_id?: string, tab?: CANVAS | PRODUCTION | CONSTRUCTION}
```

Stock available for construction includes unreserved location inventory and
same-world STORAGE inventory. Machine input/output buffers are displayed as
buffered but never counted as spendable. Rates use authoritative actual cycle
rates multiplied by recipe quantities; routers are not producers. Material
deficits aggregate remaining construction requirements before subtracting stock.
Recipe dependencies are bounded, cycle-safe, and limited to the unlocked palette.
Producer selection favors an existing configured producer, then buildable
equipment and mapped-resource recipes before finite-stock recycling. Terminal
extraction dependencies refer only to compatible, actually mapped resource fields.
No localized prose or speculative command kind is generated by this projection.

## Integrated verification — 2026-09-10

The primary integrator received all implementation handoffs, reviewed the changed
surfaces, and directly ran the following focused targets to successful exits.
These are primary-run results, not merely worker-reported passes:

- Domain/content (9): `factory_operations_projection_test`,
  `factory_industrial_loop_test`, `factory_grid_simulation_test`,
  `factory_starter_construction_test`, `factory_production_domain_test`,
  `factory_workspace_contract_test`, `asset_conservation_test`,
  `content_planner_contract_test`, `core_integrity_test`.
- Factory UI/integration (4): `factory_operations_ui_test`,
  `factory_workspace_ui_test`, `factory_production_workspaces_ui_test`,
  `factory_workspace_main_integration_test`.
- UI platform/localization (8): `responsive_ui_policy_test`,
  `ui_scale_contract_test`, `responsive_ui_matrix_test`,
  `ui_domain_integrity_test`, `localization_catalog_test`,
  `ui_english_localization_smoke_test`, `ui_chinese_localization_smoke_test`,
  `ui_input_accessibility_test`.

The new-game loop uses actual application commands and opening resources: mining,
iron/copper refining, frame/electronics/metal-stock production, physical storage,
then a depot, foundry and eight additional power units funded by new production.
It checks per-item custody, automatic delivery events, deterministic priority,
manual-funding isolation, split-time behavior and cancellation refunds.

The UI regression fixtures now explicitly enter Canvas from the default Overview;
keyboard access activates that tab using `ui_accept`, then still exercises the
palette with focus/down/accept. Main integration disables ambient frame simulation
so explicit clock-step assertions are deterministic. Per-cycle recipe yield,
live buffers, machine shortages, construction constraints and exception counts
have separate assertions.

All four rendered capture runs succeeded after final corrections. See
`docs/art/factory-ui-concept-and-qa.md` for paths and visual-review scope.
Godot runs were serialized; no user save was written. The aggregate release
runner and full J1–J10 journey runtime suite were deliberately not run.
