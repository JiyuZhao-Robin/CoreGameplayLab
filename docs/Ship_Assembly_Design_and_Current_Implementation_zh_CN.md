# 舰船装配设计理念与当前实现

> 当前实现快照：2026-09-03
> 产品版本：`1.32.0-ship-role-cutover`
> 存档 Schema：`38`

> 当前界面范围：三栏“舰船装配蓝图”已经接入主游戏的舰队 → 船厂页面，正式替换旧的装配预设、直接安装、移除和替换插件 UI。独立 Demo 暂时保留为审查入口，但只继承同一个生产编辑器组件，不再维护第二份逻辑。

> 当前内容审查范围：为了重构舰船 UI 框架时不被未达质量线的内容干扰，界面结构、子页、面板和交互全部保留，但蓝图资源库暂时只注入已经从 Demo 迁移并审查过的 Lunar Pathfinder 与 7 个 Demo 模块。其余 14 个舰体和 11 个模块仍完整保留在领域数据中，没有删除、改写或迁移存档，只是不在当前舰船蓝图页面展示。

> 可读性策略：主游戏只使用顶部统一的 75%、100%、125%、150%、175%、200% 手动界面比例；独立审查 Demo 在自己的顶部提供同样选项。窗口或输出分辨率变化只改变可用界面空间，不会自动改变字号；根节点始终保持 `scale = Vector2.ONE`，避免把已经渲染的文字插值放大。字体显示缩放与装配画布自身的 20%–500% 工程缩放彼此独立。切换字号会保留画布 zoom 和观察中心；资源卡会按真实字体高度增长，150% 以上的画布节点使用名称优先 LOD，避免放大文字互相覆盖。

本文总结当前项目中“舰船安装”的正式含义，即舰船模块装配（Ship Assembly / Loadout），并以当前代码、内容数据和专项测试为准。旧文档中“改装只消耗 BOM 差额”“尚无可视化装配编辑器”等描述已经过时，不代表当前实现。

## 1. 一句话概括

舰船装配不是给舰船增加一个抽象战力数字，而是让玩家在舰体的物理插槽、接口类型、尺寸和工程预算内亲自定义一套模块组合。编辑器保存的是“蓝图设计意图”，不会立刻建造或改装实体舰船；后续由星港/船厂根据是否存在可用同型舰体，决定进入改装装配或先造舰体再装配。

## 2. 术语与对象边界

| 概念 | 当前数据 | 含义 |
|---|---|---|
| 舰体定义 | `content.ships` | 舰体尺寸、插槽、允许模块尺寸、质量/电力/散热容量、基础战斗与货运参数 |
| 舰体建造计划 | `content.ship_construction_projects` | 舰体的解锁与建造规则、基础成本、默认模块和船厂工程等级要求 |
| 舰船设计 | `state.ship_designs` | 在装配画布中创建的命名设计，保存舰体、模块节点、位置和玩家连线，用于建造新舰 |
| 旧装配预设 | `state.saved_loadouts` | 仅为旧存档反序列化兼容保留；主游戏已无创建、应用、删除命令和 UI，不再属于活跃工作流 |
| 实体舰船 | `state.ships` | 具有永久 ID、名称、状态、地点、服役记录和当前已安装模块的资产 |
| 普通模块 | 模块定义 ID | 不是库存实体；应用装配时按完整 BOM 现场制造并安装 |
| 特殊装备 | `state.equipment_instances` | 有独立 `EQUIP-*` UUID、存放/预留/安装状态和唯一所有权的稀有资产 |

“舰船设计”现在是新舰建造和已有同型舰改装共用的唯一玩家配置来源。旧装配预设不会再由主游戏读取或创建。

## 3. 核心设计理念

### 3.1 管理设计，而不是管理普通零件库存

普通舰载模块被视为“设计定义 + 制造 BOM”，不作为可堆叠、可运输、可囤积的库存物品。造船或改装时，星港直接消耗原材料制造目标装配所需的整套普通模块。

这样保留了工业成本和供应链压力，同时避免把舰船装配变成逐件搬运、找库存和管理旧零件的行政负担。

### 3.2 玩家亲自装配，不使用模板自动连线

新设计从空白画布开始。主游戏与独立审查 Demo 都允许玩家提前记录设计意图，但不会因此解锁舰体、获得建造权限或绕过模块进度要求。玩家拖入舰体和零件后，必须把每个零件连接到舰体中的兼容插槽。拖入节点不会自动生成连接，只有玩家建立的连接才进入设计存档。

### 3.3 舰体是有物理拓扑的装配背板

舰体不是一排同质槽位。当前视觉与规则共同表达：

- 能源核心位于舰体中央，是画布设计的必需模块。
- 推进接口位于舰体上部。
- 武器与特殊插件分布在舰体两翼。
- 护盾、货舱等结构件位于舰体下部。
- 小型舰体插槽少、尺寸上限低；大型舰体拥有更多、更大的插槽。

舰体轮廓、长宽、插槽直径与画布比例使用统一物理尺度，因此大型舰体在画布上确实比小型舰体更大，而不是只更换一张图标。

### 3.4 接口形状承担规则提示

| 安装族 | 形状 | 当前对应内容 |
|---|---|---|
| 武器 | 三角形 | 火炮、能量武器等 |
| 特殊插件 | 五边形 | 传感器、火控、维修、深度勘测等 |
| 推进 | 菱形 | 基础与高级推进器 |
| 船体结构 | 方形 | 护盾、货舱、大宗/低温货运结构等 |
| 能源核心 | 圆形 | 民用与高输出反应堆核心 |

接口的方向、安装族、形状、占用状态和尺寸等级都必须匹配。蓝色方形是统一的 `STRUCTURE` 物理接口，而不是护盾专用槽：民用护盾、货舱扩展和船体装甲可以任意占用同一组结构接口。Lunar Pathfinder 明确拥有两枚结构接口，因此允许两护盾、两货舱、两装甲或任意两件混装。未连接插槽为灰色空心；拖动连线时只有兼容插槽高亮；连接完成后插槽按类型着色并变为实心。

### 3.5 UI 表达意图，领域层决定真伪

画布负责交互反馈和草稿，不直接修改舰船或船厂状态。保存和建造前必须再次经过 `Game.ship_design_validation()`；即使伪造 UI 数据，也不能绕过领域校验。

### 3.6 装配必须产生真实工业成本和时间成本

装配不是免费切换标签：

- 新舰成本 = 舰体建造成本 + 初始装配中全部普通模块的 BOM。
- 改装成本 = 目标装配中全部普通模块的 BOM，而不是与旧装配的差额。
- 相同普通模块不会抵扣，因为普通模块不是跨改装周期永久存在的独立资产。
- 制造时间与安装时间分别计算，但当前合并为一个连续的 100 段改装项目。
- 取消改装会恢复原装配，但已投入的制造材料不返还。

### 3.7 舰船职责来自当前装配

舰体本身不授予任务能力；能力由当前安装模块累加。当前主要影响包括：

- 武器、护盾、命中、电子战、弹药和攻击循环等战斗参数。
- `long_range_scan`、`survey_support` 等勘测与远征能力。
- `bulk_freight`、`insulated_cargo`、`high_speed_freight` 等专用运输资格。
- 模块货舱容量对物流吞吐的增量。
- `repair_support` 对停靠舰船修理速度的支援。
- 推进、隐身、抗辐射等路线或任务门槛。

Schema 38 已明确废止舰船承担常规采矿、采气和施工生产的旧路线；这些长期工业工作现在归属于方格工厂世界。舰船保留移动任务、物流、勘测、战斗和舰队支援职责。

### 3.8 普通模块与特殊装备采用双重资产语义

普通模块只保存定义 ID，改装时重新制造；Boss 或任务回收的特殊装备则保留 UUID，只能由一艘舰船占有，拆下后回到星港存储。这个边界让常规模块保持低管理负担，同时保留稀有战利品的唯一性。

## 4. 当前闭环

```text
内容数据
  └─ 舰体、插槽、模块、BOM、建造计划
       ↓
空白装配画布
  └─ 拖入舰体与模块 → 玩家手动连线 → 领域校验
       ↓
命名舰船设计（ship_designs）
  ├─ 无同型舰体 → 船厂建造订单 → 快照模块清单 → 分段消耗完整 BOM → 新实体舰
  └─ 有同型停靠舰体 → 蓝图改装订单 → 制造完整 BOM → 安装到目标实体舰
       ↓
实体舰船（ships）→ 战斗 / 远征 / 勘测 / 物流读取当前装配
```

### 4.1 整个舰船 Tab 的信息、任务与质量线

舰船 Tab 是一个完整的舰队资产工作区，而不是单一“换插件”弹窗。现有 UI 框架保留以下入口：

| 子区 | 展示的信息 | 玩家要完成的任务 |
|---|---|---|
| 舰船名册 | 实体舰身份、舰体型号、状态、维护、编队、职责和服役记录 | 查看与组织已经建成的舰船 |
| 编队与补给 | 编队、阵位、交战/撤退策略、补给目标和指挥容量 | 让实体舰形成可执行任务的舰队 |
| 造船与安装 | 蓝图资源库、装配画布、接口拓扑、工程预算、兼容性、建造/改装估算 | 创建、命名、保存和载入舰船设计，并显式交给船厂 |
| 维修与档案 | 改装、维修项目和退役舰记录 | 跟踪舰船生命周期，而不是编辑蓝图 |
| 任务入口 | 可用任务、舰队需求与执行状态 | 把满足条件的舰队派往真实任务 |

其中“造船与安装”继续严格使用左—中—右三栏：左侧是可拖入的舰体/模块，中间是玩家正在设计的舰船蓝图，右侧是设计的工程含义。当前清掉的是未审查的内容实体，不是这套 UI 框架。

完成质量不能以“控件出现、代码能跑”为标准，至少要达到：

- 三秒内读懂页面用途；视觉注意力依次是舰船、安装拓扑、模块身份、工程数据。
- 1440×900 下默认字号可读，顶部手动比例控制文字与符号，窗口尺寸变化不产生模糊插值缩放。
- 舰体和画布实体在近景保留 4K 清晰度；资源目录只使用轻量预览图，不为 88px 卡片同步解码 4K 原图。
- 打开舰船页面不能有可感知的长停顿；空白编辑器不得预加载尚未放入画布的 4K 舰体、FX 遮罩和模块原图。
- 拖拽、选择、连接、断开、删除、平移、20%–500% 缩放、适配视图、保存、载入、新建和位置/连线持久化形成真实闭环。
- 所有质量、电力、热量、插槽、BOM、建造与改装结果来自同一领域 API；界面不显示伪造工程数据，也不在保存蓝图时直接生成实体舰。

## 5. 已经实现的部分

### 5.1 数据驱动的舰体与模块内容

当前 `data/content.json` 包含：

- 15 个舰体定义和对应的 15 个建造计划；开局状态另有一个实体舰实例。
- 18 个模块定义：17 个普通模块、1 个 UUID 特殊装备。
- 5–11 个插槽的舰体规模跨度。
- `weapon / shield / drive / utility / core` 五类逻辑槽位。
- 逻辑用途与物理安装接口分离；`installation_interfaces` 可直接声明 `weapon / structure / drive / utility / core` 容量，Lunar Pathfinder 的结构接口容量为 2。
- S、M、L、XL、XXL 五级接口系统；当前模块内容实际使用 S、M、L，大型舰体已提供 XL、XXL 插槽上限。
- 17 条普通模块 BOM 配方，覆盖当前所有普通模块。

内容校验器会检查舰体插槽总数、默认装配合法性、普通模块经济路径，以及默认造船计划不能凭空生成特殊装备。

### 5.2 可交互装配画布

`ShipAssemblyMapView` 已实现：

- 空白画布起步，以及“舰船 / 零件”两个拖拽 Palette。
- 当前审查阶段只展示 Demo 已迁移的 1 个舰体和 7 个模块；领域中的其他舰船内容保持原样，待逐项达到视觉质量线后再重新接入。
- 画布中最多一个舰体，但可以放置多个同定义模块节点。
- 点阵网格、20 像素吸附、选择/平移工具、20%–500% 缩放和“适配全部”视图；重复的右下角小地图已删除。
- 舰体与模块节点移动、选择、退格删除、拖入底部垃圾桶删除、断开和重新连接；前向 `Delete` 不再删除模块。
- 直角短引线—共享横轨—短接入布线，带圆角和节点避让。
- 自定义连线绘制、命中测试与选中反馈。
- 连接过程中兼容、静默、不兼容、已连接等插槽视觉状态。
- Lunar Pathfinder 使用紧贴透明轮廓裁切的 4K 顶视舰体、4K FX 遮罩、克制的舰体辉光、结构能量流与微光活动；逻辑尺寸仍由 44m × 132m 物理数据决定，而不是由贴图像素决定。
- 模块使用 4K 透明图、技术底盘、约 2.5:1 节点比例、内嵌可视接口与独立路由端点；节点会朝向舰体，并支持上下左右四边出线。
- 连线使用直角工程路由、多层低亮绘制、稀疏数据包、接口到达响应、命中测试和相关性高亮。
- 远景按 LOD 隐藏英文副标题、微型元数据和不可读文字；舰体微光也随远景收敛。
- 根据舰体轮廓与插槽直径自动寻找不越界、不重叠的插槽位置。
- 侧栏查看舰体、模块指标、当前校验结果和整舰材料清单。

### 5.2.1 主游戏与 Demo 共用的生产三栏界面

`ShipAssemblyBlueprintEditor` 目前已经同时服务主游戏船厂和 `ship_art_deployment_demo` 审查壳：

- 顶部安静的命令栏：当前蓝图、载入蓝图、新建蓝图；主行动仍固定在右下角“保存设定 / SAVE BLUEPRINT”。
- 左侧资源库严格只有“舰船 / SHIPS”和“零件 / MODULES”两个顶层页签，模块页提供搜索和武器、推进、防御、核心、功能、结构分类筛选。
- 中央继续复用真实 `ShipAssemblyMapView`，没有新建第二套画布、路由、命中测试或连接模型。
- 右侧工程数据面板支持蓝图摘要、按真实连接统计的接口占用、质量/功率/热量、真实建造与改装 BOM、真实时间估算、需求/兼容性、舰体检视和数据驱动模块检视。
- 蓝图名称、舰体、模块节点、节点坐标和逻辑连接通过原有 `Game.save_ship_design()` 保存；保存不会调用 `enqueue_saved_ship_design()` 或 `begin_ship_refit()`。
- 顶部“新建”和“载入”已经连接到真实画布草稿；保存后方案立即进入载入列表，载入会恢复名称、舰体、模块坐标、连接、测量信息和 `SAVED / MODIFIED` 状态。
- “保存设定”会在领域校验通过后立即写入 `LocalSaveRepository`，不再依赖 15 秒自动保存窗口；写盘失败会明确保留会话内草稿并显示错误。
- 编辑器可以保存尚未解锁的舰体设计，但右侧会明确提示“解锁后才能提交船厂”；真实入队仍由 `enqueue_saved_ship_design()` 和 `enqueue_ship_plan()` 强制检查解锁状态。
- 工程摘要会报告当前存在可改装同型舰体还是需要先建造舰体；保存本身仍不执行实体操作。主游戏下方的“船厂交接”才可显式创建建造订单或对同型实体舰发起改装。
- 主游戏进入该工作区时隐藏外层重复的资源栏、检查器和底部命令坞，保证左资源、中央画布、右数据三栏占据主要空间；离开后恢复原游戏外壳。
- 编辑器统一使用功能形状（三角武器、菱形推进、蓝色方形通用结构、五边形功能、圆形核心），旧页面和旧连接表现已从主游戏移除。

### 5.2.2 打开页面卡顿诊断与处理

卡顿的主要来源不是连线算法，而是两条同步重建路径。第一，资源目录在创建卡片时立即调用 `load()`：原实现把画布用的 4096×4096 模块图直接塞进约 88px 的左侧缩略图，一次进入页面会触发五张模块 4K 图的同步加载；完整内容目录还会一次创建 15 张舰体卡和 18 张模块卡。五张模块 4K PNG 的源文件合计约 48.6 MB，解码后的纹理内存远高于文件体积，舰体 4K 底图和 FX 遮罩还会继续增加首次加载压力。第二，主游戏每次收到领域状态刷新都会清空并重建整个船厂页，连尚未保存的画布、节点和已加载 4K 实体也会一起销毁后重建。

当前处理保持高清画布不降级：

- 蓝图目录从 15 个舰体、18 个模块收敛为 1 个舰体、7 个已审查 Demo 模块。
- 左侧舰体卡使用 727×2048 预览图，模块卡使用 1254×1254 预览图。
- 4096 级模块原图、舰体底图和 FX 遮罩只在玩家真正把实体放入画布或载入已有蓝图时加载。
- 画布节点仍使用 `_4k` 原图，因此 500% 近景质量没有被缩略图优化牺牲。
- 船厂状态刷新现在复用同一个编辑器和画布实例，只刷新已保存方案列表、工程数据和下方船厂交接/队列；当前草稿、视角和 4K 实体不再被反复销毁。

### 5.3 双层连接校验

画布层立即拒绝：

- 反向连接或非“模块 → 舰体插槽”的连接。
- 物理安装族/形状不匹配；同属 `STRUCTURE` 的护盾、货舱和装甲不会因逻辑用途不同而被拒绝。
- 模块尺寸等级大于插槽上限。
- 一个模块连接多个插槽，或一个插槽被多个模块占用。

领域层保存前重新检查：

- 建造计划存在；设计意图保存可以跳过计划解锁项，但不能跳过后续船厂入队或改装交接检查。
- 设计中恰好有一个与计划匹配的舰体。
- 模块存在、已揭示，节点 ID 和连接目标有效。
- 每个模块恰好连接一个有效插槽。
- 接口族和模块尺寸合法。
- 中央能源核心已经安装并连接。
- 各物理接口池数量未超限。
- 模块总质量、电力需求和热负荷不超过舰体容量。

### 5.4 命名设计与持久化

玩家可以：

- 为同一舰体保存多个命名舰船设计。
- 重新载入设计并继续编辑。
- 更新或删除已保存设计。
- 保存模块节点位置和玩家建立的连接，而不只保存最终模块列表。
- 通过 Save Schema 序列化 `ship_designs`、下一个设计序号和相关船厂运行态。
- 编辑器的保存按钮会立即把当前领域状态写入本地存档；自动化回归会从独立 `LocalSaveRepository` 重新读取并核对该设计。

进入船厂时会再次校验设计，并把模块清单快照到订单的 `custom_modules`；之后修改或删除原设计不会改变已入队订单的实际装配内容。

### 5.5 真实船厂订单

当前船厂已实现：

- 从已保存设计创建 1、5、20 艘批次订单；领域接口允许 1–100 艘。
- 队列持久化、上移/下移、取消、阻塞原因和进度展示。
- 船厂工程等级门槛与星港供电/速度修正。
- 每艘舰船以 100 个进度段逐步消耗材料。
- 舰体基础材料、固定成本和完整初始装配 BOM 的统一计算。
- 缺料时进入 `BLOCKED`，材料恢复后继续推进。
- 造船需求进入共享 Demand Registry，供经济诊断与规划器读取。
- 批量订单逐艘完工，每艘获得独立 `SHIP-*` ID、名称、服役时间和实际模块清单。
- 舰船属于离散资本项目，不接受生产力额外产出，避免产生免费进度或额外舰船。
- 取消订单时已消耗材料不返还，尚未消耗部分不再继续承诺。

### 5.6 现役舰改装

主游戏现在只允许从船厂中的已保存蓝图发起实体舰改装：

- `ship_design_refit_candidates()` 只列出与蓝图舰体型号匹配的实体舰。
- `ship_design_refit_availability()` 会先重新校验持久化节点与连接，再复用统一的 `ship_loadout_availability()` 检查停靠状态、模块设计、特殊装备所有权、装配合法性和完整 BOM 库存。
- `begin_ship_design_refit()` 把已校验蓝图 ID 和目标模块清单交给现有 `begin_ship_refit()` 事务；旧的装配预设、直接安装、移除、替换应用命令及按钮均已删除。
- 只有状态正常、已停靠且未封存的舰船可以改装。
- 改装启动后舰船进入 `REFITTING`，暂时清空现有安装位，并被排除在任务之外。
- 普通模块完整 BOM 在项目开始时一次性扣除。
- 制造时间和安装时间分别保存，当前合并为一个 100 段连续项目。
- 完工后安装目标模块、恢复 `DOCKED`，并记录来源蓝图 ID 与改装统计。
- 取消后恢复原装配和特殊装备所有权，但不退还普通模块制造材料。

### 5.7 特殊装备唯一性

特殊装备已实现的部分包括：

- 任务效果生成独立 `EQUIP-*` 实例。
- `STORAGE / RESERVED_REFIT / INSTALLED` 状态。
- 同一实例不能同时安装在两艘舰船上。
- 改装时可以复用本舰原装备或从星港存储预留。
- 被替换的特殊装备在改装完成后回到存储。
- 取消改装会恢复原舰的特殊装备所有权。
- 拆解舰船时特殊装备返回存储，而不是作为普通材料销毁。

### 5.8 装配对其他系统的实际影响

当前装配不是展示数据，已有多个系统直接读取它：

- `CombatResolver` 将武器、护盾、装甲、精度、电子战、攻击触发器和弹药规则汇入单舰战斗演员。
- Survey Mission 按安装能力检查逐级勘测资格，并用能力值缩短任务时间。
- Expedition 节点按推进、武装、护盾、传感器等能力检查舰队是否满足条件。
- Logistics 按真实货舱容量和所需模块能力决定专用运输舰是否合格，并计算路线运力。
- 舰队修理和远征支援速度读取 `repair_support` 与 `survey_support`。
- 名册会从装配实时投影大宗货运、低温货运、维修支援、勘测支援、武装等职责标签。

## 6. 当前尚未统一或尚未完成的边界

这些项目不能写成“已经完整实现”：

1. **独立 Demo 尚未删除。** 它是共享生产组件的薄审查壳，按本轮要求要等主游戏审查通过后再移除。
2. **旧装配预设字段仍保留在存档兼容层。** 主游戏已经没有相关命令和 UI；字段暂不移除，以免只为界面切换引入 Save Schema 迁移。
3. **特殊装备的画布路径尚未闭环。** 特殊装备 UUID、存储和改装所有权已经实现，但画布资源库/保存校验目前没有为具体 UUID 建立预留关系；自定义造船订单仍只快照模块定义。这条路径仍需增加“必须拥有具体 UUID、不能由船厂复制”的约束。
4. **插槽规格仍有生成式简化。** 每个舰体使用一个统一的最大接口尺寸；Lunar Pathfinder 已显式声明物理接口容量，其他舰体的 Utility“特殊/结构”数量仍由默认装配推导，尚未逐插槽写入内容。
5. **连线目前表达安装关系，不表达系统网络。** 节点位置和布线路径不会产生射界、相邻加成、供电拓扑、热流或损伤分区；模拟最终读取的是通过校验得到的模块清单。
6. **工程反馈尚无变化对比与任务适配评分。** 当前已经显示质量、电力、散热、连接占用、BOM 和时间估算。
7. **部分历史文档和旧测试仍引用已退役规则。** 例如旧的采矿激光/采气/施工舰职责、BOM 差额改装和“无可视化编辑器”描述，应以 Schema 38 当前代码与本文为准。
